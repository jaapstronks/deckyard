# Essential fields: the audit of the core types

A field can be `essential` (D211): when it is empty, the editor shows it without hover as "something goes here", instead of waiting for a hover. This is a separate property from `required`. `required` decides whether a slide may be saved or published without a value. `essential` decides what an empty field shows while someone edits. For a list, `essential` refers to the first entry; later entries are always optional. The mechanism is described in [`wysiwyg-inline-editing.md`](wysiwyg-inline-editing.md). This page lists the per-field decisions for the <!--gen:slide-type-count-->35<!--/gen:slide-type-count--> core types (B435 PR 2), so a reviewer can test them one by one.

**The rule of thumb**: does an empty slide of this type look _broken_ without this field, rather than _sober_? Every field was judged against it separately. No field became essential through a batch rule such as "every heading is essential". `image-slide.title` shows why: it is a heading, but the image carries the slide.

**Not listed**: enum, number and boolean fields (layout, variant, background, colour, timing), the accessibility fields (`a11yTitle`, `a11ySummary`), `alt` and focus fields, and the slide-background family (`slideBg*`, `slideLogo`). These are settings with a working default, or descriptions of other content. An empty one never makes a slide look broken, so none of them is essential.

## What an empty essential field shows

The editor picks the affordance from the field's kind and from what the renderer draws. There is no per-type code:

| Behaviour       | When                                                                                                                     | Example                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| **placeholder** | Text field whose element the renderer draws even when empty                                                              | "Add title" in the title box of a content-slide |
| **chip**        | Text field whose element the renderer leaves out when empty                                                              | "+ Title" above a cycle diagram                 |
| **add**         | Empty list                                                                                                               | "+ Add item" under a funnel                     |
| **hint**        | Empty single image frame                                                                                                 | "+ Add image" on an image-slide                 |
| **renderer**    | Field without an inline affordance (set in the inspector), or an image list whose empty frames the renderer draws itself | The embed's "Paste an HTTPS URL" note           |

The table below is also a test. `tests/inline-essential-visibility.test.js` holds the schema to it in both directions: every row must be declared, and nothing else may be. It then renders every row empty and checks the behaviour named here.

## Form decisions made in the audit

- **An inspector-only field is still marked essential if the slide looks broken without it** (`chart.data`, `embed.embedUrl`, `video.source`, `custom-html.html`). `essential` describes the slide, not the editor: the same flag tells an agent which fields make a slide look complete (B435 PR 3). In the editor, such a field's empty state is the renderer's own note, which is visible without hover. No new canvas mechanism was added for it.
- **An image list whose empty frames the renderer draws gets no always-visible chip** (`image-set.images`, `logo-wall.logos`). Each empty frame already shows an icon and label without hover. That frame is the image's in-box placeholder, and it plays the same role that "Add title" plays for text. A chip on every empty frame would give one fact N answers. The flat single image (image-slide, image-text-slide) keeps the hint from PR 1.
- **An empty `rows[]` on text-blocks is the empty state, not a cue to read the legacy fields.** Before this audit, `rows: []` fell back to the numbered fields and drew a row with no inline hooks, so an essential `rows` had no "+ Add". The migration now drops the numbered keys once folded (D216, review of PR 2): left standing, they made every later `rows: []` on that slide read as "still to fold", since nothing persists `schemaVersion` and the chain runs on every read and write, so emptying the rows brought them back on the next read. After one read, `rows[]` is the only shape a stored text-blocks slide carries, and since B452 it is the only shape anything reads: `resolveRows()` reads the array alone, the numbered field definitions and the card guard for decks without `rows` are gone, and the numbered reader lives in the v1 → v2 step of `schema-version.js`.
- **Only team-cards needs a CSS rule for a renderer note under the "+ Add".** logo-wall's "add logos" note appears only outside the editor. In edit mode the empty wall draws a placeholder cell instead.
