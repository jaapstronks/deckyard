# CSS layers and styling boundaries

Deckyard's CSS is split along one line: the **slide** (themed, rendered the same on screen, in PDF and in an agent's preview) versus the **application** around it (theme-independent chrome). This page is the map of that split: which layer a stylesheet belongs to, what it may read, and how the generated aggregators keep the order. The token namespace itself is in [CSS tokens](css-tokens.md), ownership of app sheets in [CSS ownership](css-ownership.md), the breakpoint ladder in [CSS breakpoints](css-breakpoints.md).

## Slide styling

- Theme variables are scoped to `.slide`, so the application UI stays theme-independent. The `--t-*` → slide-variable layer is `client/styles/slides/00-theme.css`, loaded by `client/styles/slides.css` right after the tokens and nowhere else (D268).
- Slide styling lives under `client/styles/slides/*` and is included via `client/styles/slides.css`. It reads `--slide-*` roles, never `--app-*` or `--ps-*`.
- Don't hardcode brand colours or fonts inside slide templates. Prefer CSS variables: `--t-*` theme variables → `.slide` variables → component CSS.

## App chrome

- App tokens are `--ps-*` (scale), `--app-*` (mode-bound role) and `--z-*` (stack), all defined only in `client/styles/shared/ui-tokens.css`. Anything else is component-local and named after its component ([CSS tokens](css-tokens.md) § The namespace rule, `tests/app-css-tokens.test.js`).
- The presenter chrome around the deck (topbar, stage, console, progress, start curtain, present window) is the viewer layer, `client/styles/viewer/`, aggregated into `client/styles/viewer.css`. `app.css` and `export.css` load it before `slides.css`; the embed and the MCP preview do not (D267).
- Four app CSS layers load in order: tokens (`client/styles/app/tokens.css`), primitives (`client/styles/shared/primitives.css` and `client/styles/app/components.css`), viewer chrome (`client/styles/viewer.css`), then feature chrome.
- Feature CSS lives in `client/styles/app/<feature>/`, named after its folder in `client/views/` (`shell/` is the shared frame); `app/<feature>.css` aggregates each folder. A new sheet goes in its feature folder and in the manifest, never loose in `app/`.
- Shared DOM widget CSS lives in `client/styles/app/components/`, with a generated `components.css` aggregator. `tests/css-ownership.test.js` requires a JS string reference in the matching feature (or `lib/dom` for components and shell), with an exact shrinking debt list ([CSS ownership](css-ownership.md)).

## Generated aggregators

The `slides.css`, `viewer.css`, slide-tier and per-feature app aggregators are generated by `scripts/generate-slide-css-aggregators.js` (`npm run gen:slide-css`) and guarded by `tests/css-aggregators.test.js`. Never hand-edit an aggregator: declare the sheet in the generator's manifest and regenerate.

Width-based `@media` queries sit on the shared breakpoint ladder ([CSS breakpoints](css-breakpoints.md), `tests/css-breakpoints.test.js`).
