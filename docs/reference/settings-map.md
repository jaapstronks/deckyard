# Settings map: scopes, controls and configuration

Snapshot: Deckyard **1.77.2 with the settings scope changes (B803)**, inspected on 2026-10-20. This reference describes the current `/settings` page, its fourteen tabs and their persistence and authorization boundaries. Theme and slide-type editor internals are separate workbenches; their management actions are listed here.

## Scope and access

The settings menu groups tabs as Personal, Organization, Design and Installation. The [tab registry](../../client/views/settings/tab-registry.js) defines one technical address per tab; inaccessible hashes resolve to Account. Installation controls follow instance admin status, organization policy follows the active organization admin gate, and API keys are personal when `publicApi` is enabled. [Page access](../../client/views/settings/index.js) is calculated when the page mounts.

| Term                                       | Persistence and API boundary                                                                                                                                               | Who can write                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Personal**                               | Instance-wide `user_settings` for one person, keyed primarily by stable user ID with an email fallback. `GET/PUT /api/settings/me`; not scoped to the active organization. | An authenticated user with an email writes their own preferences. See [settings storage](../../server/storage/settings.js) and [settings routes](../../server/routes/api/settings.js).                                                                                                                                                                                                                                                                             |
| **Instance**                               | Singleton `app_settings`; shared by all organizations. `GET/PUT /api/settings/app`. Email template overrides and their default locale also have instance-wide tables.      | App settings and template writes require the instance `isAdmin` flag. App reads require authentication; webhook settings are removed for non-admin readers. See [settings routes](../../server/routes/api/settings.js) and [template storage](../../server/storage/email-templates.js).                                                                                                                                                                            |
| **Organization policy**                    | Active organization's `organizations.settings`, exposed by `GET/PATCH /api/settings/organization`.                                                                         | Keys other than `disabledSlideTypes` require instance admin and, in multi-organization mode, admin/owner membership in that organization. `disabledSlideTypes` requires designer capability. | **Organization records**                   | Organization profile, memberships, custom fonts, custom themes and custom slide types are separate records.                                                                | Profile edits require organization admin/owner; deletion requires owner. | **Personal API access in an organization** | API keys are filtered by both `organization_id` and caller `owner_email`.                                                                                                  | The key API and Settings tab require authenticated email; the tab also follows the `publicApi` feature gate. Organization policy uses [`isOrganizationAdmin`](../../shared/organization-role.js): instance admin, narrowed by active admin/owner membership when present. Installation settings use the backend's instance-only admin check. Organization ownership alone permits profile and membership operations but does not grant organization policy. Designers manage custom themes without theme policy writes. An empty stored theme allowlist inherits installation `ENABLED_THEMES`; saving explicit checked IDs does not clear that restriction accidentally.

In multi-organization mode, a policy admin without designer capability sees only the filtered theme list, even in the policy editor. They cannot re-enable a theme excluded from that list; the full list requires the existing designer capability on `GET /api/themes?all=1`.

The registry and [English](../../client/i18n/en/settings.json) / [Dutch](../../client/i18n/nl/settings.json) catalogues define the current labels. The sidebar is a labelled navigation of real `#<key>` links with `aria-current` on the active one. Following a link adds a browser-history entry, so Back, Forward and reload restore the section; `/settings` and an unknown or unreachable hash are replaced in place by Account. Focus moves to the section heading after a switch. On narrow screens one opener names the current section and expands the same links as vertical groups; Escape folds it back. The topbar arrow is an Overview link to `/app`, not browser Back. Leaving a section whose explicit-Save form (display name, email sender, webhooks, slide type curation) has unsaved changes asks first; cancelling keeps the edits and the address. ## Presentation settings

Presentation settings belong to the deck and require write access to that deck. They are the **Deck settings** pane of the editor's right-hand rail, beside the canvas they change (below 1024 px the rail is a drawer over the canvas, D339); the editor's ⋯ menu opens it. Changes save as they are made; text fields generally save on blur, and closing the pane lets a focused field blur first. Tags use their own immediate save request. A lock on the selected slide does not block the pane; a read-only editor does. See the [pane](../../client/views/editor/deck-settings/index.js#L167) and [shared save service](../../server/services/save-presentation.js#L16).

The pane has one address per section: `/app/:id?panel=settings&section=<key>`, with `general` (language, tags, description), `appearance` (theme), `playback` (builds, reveal style, transitions, timed slides), `publishing` (Q&A, author on preview, feed), `analytics` and `live-video`. Opening it adds one browser-history entry; switching sections replaces that entry. Back closes the pane and Forward reopens it on the same section, both without reloading the editor: the selected slide and the edited language stay as they are (the [router keeps them](../../client/lib/state/router.js) for the claimed keys). Reload or a shared link opens the pane on its section. An unknown section, or `analytics` where the installation has no analytics, is corrected in place to `general`. Closing removes only `panel` and `section`; every other query key stays. Focus moves to the pane heading on open and back to the opener on close. [Route](../../client/views/editor/deck-settings/route.js#L37).

## Installation environment inventory

Environment variables configure the installation and are set by its operator. They are not user-account preferences. Existing process variables take precedence over the local environment file, as implemented by the [environment loader](../../server/config/env.js#L28). The canonical list, descriptions, defaults and constraints are in [`.env.example`](../../.env.example); the [manifest test](../../tests/env-manifest.test.js#L2) checks that engine reads remain documented. Variable names below are grouped for navigation; no deployment values are reproduced.

Theme defaults and allowlists can be overridden by stored organization settings. Analytics retention variables seed the values subsequently managed through instance settings. External analytics providers have documented environment fallbacks. Infrastructure credentials, bind addresses, database/storage configuration, proxy policy, browser executables, timeouts and debug controls remain deployment configuration. Raw analytics head snippets and Google Tag Manager are explicitly environment-only.
