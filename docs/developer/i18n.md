# Internationalization (i18n)

This guide covers the UI internationalization system for the presentation system.

## Directory Structure

```
client/i18n/
├── manifest.json           # The source of truth: 12 locales (id/label/tier),
│                           # the reference locale, and the module files with
│                           # the loader that reads each — see below
├── en/                     # English (reference language)
│   ├── common.json         # Common UI strings
│   ├── auth.json           # Login, forgot/reset password
│   ├── editor.json         # Editor interface
│   ├── list.json           # Presentation list, libraries
│   ├── share.json          # Sharing, viewer, moderation
│   ├── settings.json       # Settings, admin panel
│   ├── presenter.json      # Presenter mode
│   ├── slide-types.json    # Slide type labels/options
│   └── follow.json         # Follow-view chrome (separate loader, keyed on deck language)
├── nl/                     # Dutch
│   └── (same structure)
├── de/, fr/, es/, it/, pl/, fi/, pt/, da/, sv/, no/
│   └── (same structure)
```

`manifest.json` is the only place those lists live. Every i18n script reads it
through `scripts/lib/i18n-locales.js` rather than keeping its own copy — before B132
there were four hand-kept spellings (a fill list of 8 locales, a prune list of
12, a validate list of 12, and two different module lists), and they had drifted
apart. Adding or removing a locale or a module file is a manifest edit;
`tests/i18n-locales.test.js` fails if the directories on disk disagree.
See [`docs/reference/i18n-locale-tiers.md`](../reference/i18n-locale-tiers.md)
for what `tier`, `reference` and `loader` each mean.

The app loads the modular `<locale>/<component>.json` files directly
(`client/lib/ui-i18n.js`, `I18N_COMPONENTS`). **There is no merged flat file.**
A per-locale `index.json` used to be regenerated on every sync — read by
nothing, tracked by nothing, so it floated untracked in every working copy. B130
removed its three generators (`i18n-merge.js` and `i18n-modularize.js` are gone;
`i18n-sync.js` no longer writes one) rather than picking a tracked-or-ignored
status for a file the runtime never asks for. If an old checkout still has one,
delete it — `tests/i18n-sync-dry-run.test.js` fails on one. (The old `en.json`
output and the
`template.pot.json` extraction template went the same way earlier:
`i18n-extract.js`, which wrote them, was retired in B94 — the per-locale
`en/*.json` files are the only English source, and `i18n-fill.js --report
<locale>` does the translator hand-off.)

## Key Conventions

Use dot-notation keys with category prefix:

```javascript
t('common.save', 'Save');
t('editor.share.title', 'Share presentation');
t('slideType.textSlide.label', 'Text Slide');
```

## Using Translations

Import and call `t()`:

```javascript
import { t } from '/client/lib/ui-i18n.js';

// Simple translation
const label = t('common.save', 'Save');

// With interpolation
const msg = t('list.count', '{count} presentations', { count: 5 });
```

The second argument is the English fallback, used when:

- Translation is missing for current locale
- File fails to load

## Adding New Strings

Write the call site first — the English fallback is the source of truth:

```javascript
t('editor.foo.bar', 'Some English text');
```

Then materialize the keys. English is mechanical (the fallback _is_ the
English string); Dutch needs real translation:

```bash
node scripts/i18n-fill.js en              # write missing EN keys from fallbacks
node scripts/i18n-fill.js --report nl     # dump missing NL keys as JSON
node scripts/i18n-fill.js --apply nl out.json   # merge translations back
```

`npm test` fails if a key used in code is missing from `nl/` or `en/`, so this
is not optional — see `tests/i18n-coverage.test.js`.

`--report <locale>` answers from two sources: the static `t()` call sites and
`en/` itself. The second one matters, because the runtime-built families
(`slideType.*`, `editor.textStyle.*`, `editor.layoutVariant.*`,
`editor.inline.add*`/`remove*`) are assembled from template literals and have
no static call site — but they do have a settled English string in `en/`, so
they are translatable all the same. `tests/i18n-fill-report.test.js` pins that
the report never hides a key `en/` has and the target locale does not.

**A key lives in exactly one module file, and `en/` decides which.** `--apply`
routes a key to the module `en/` files it in; for a prefix `en/` has never seen,
`i18n-fill.js` falls back to the module most of `en/`'s keys under that prefix
already live in (B147 — it used to be a hand-kept table, and the table drifted).
That is what keeps the locale directories the same shape: before B137 the table
was the only answer, so `analytics.*` went to `common.json` in four locales
while `en/` kept those keys in `editor.json`.
`tests/i18n-duplicate-keys.test.js` pins both halves — no key in two
modules of one locale (the runtime merges them, so one copy would be dead), and
no key filed somewhere other than where `en/` files it. The third direction —
keys a locale has that `en/` does not — is
`tests/i18n-coverage.test.js` § _en/ holds every key any other locale holds_.

**Never build a translatable string by concatenation.** A key must contain the
whole sentence, with `{var}` placeholders for the moving parts, because word
order differs per language:

```javascript
t('x.days', '{n} days', { n: 30 }); // ✅
'30 ' + t('x.days', 'days'); // ❌ untranslatable
t('x.del', `Delete "${name}"?`); // ❌ only the fallback interpolates
```

## Scripts

| Script                        | Purpose                                                                                                                           |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `npm run i18n:audit`          | Find hardcoded copy that bypasses `t()`, and orphan keys                                                                          |
| `node scripts/i18n-fill.js`   | Materialize EN from fallbacks; report/apply other locales                                                                         |
| `node scripts/i18n-sync.js`   | Prune dead `slideType.*` keys, then fill missing keys with English placeholders; `--dry-run` reports the plan and writes nothing  |
| `scripts/lib/i18n-locales.js` | Reads `client/i18n/manifest.json`; exports the locale, tier, reference and module lists every script above works from (not a CLI) |
| `scripts/lib/i18n-keys.js`    | The one `t()`-key extractor (not a CLI)                                                                                           |
| `scripts/lib/i18n-fs.js`      | Repo paths, the `.js` tree walk, and locale-file read/write — the shapes the scripts used to each keep a copy of (not a CLI)      |
| `scripts/lib/is-cli.js`       | "Was this run as a script?", spelled once (not a CLI)                                                                             |

`scripts/lib/i18n-keys.js` is the **one** extractor — the fill script and the
coverage test both use it, so they always agree on what "a key the code uses"
means. It reads `t('key', 'fallback')` call sites _and_ descriptor tables, which
pass the two halves as an adjacent `<x>Key` / `<x>` property pair. That pair has
exactly one spelling; a `<x>Default` half fails `tests/i18n-coverage.test.js`.

### What the two gates each catch

`tests/i18n-coverage.test.js` guards the **keys**: everything the code asks for
must exist in `nl/` and `en/`. It is blind to copy that never asks — a label
written as a literal inside `h(...)` has no key to be missing, so it renders
English in all 12 locales and no test notices.

`tests/i18n-audit.test.js` closes that hole. `npm run i18n:audit` scans for
user-facing literals (`text:`, `title:`, `label:`, `placeholder:`, `alt:`,
`aria-label:`, `hint:`, `toast(…)`) and fails on anything not listed in
`scripts/i18n-audit-allowlist.json`. That file is a **burndown**, in the same
spirit as `eslint-suppressions.json`: each entry needs a reason, stale entries
fail the build, and the list is meant to shrink.

Legitimate reasons to allowlist rather than translate: brand and product names
(Unsplash, Matomo), language names shown in their own language, language tags
(`NL`), syntax examples (`Raleway:400,700`), and typographic specimens (`Aa`).

Two patterns are _not_ findings, and the scanner already skips both:

```javascript
// 1. literal as the t() fallback
h('div', { text: t('common.save', 'Save') });

// 2. config table built at import time, before the dictionary loads —
//    the sibling *Key prop is what gets resolved at render time
const SOURCES = [
  {
    key: 'upload',
    labelKey: 'fonts.source.upload',
    label: 'Upload Custom Font',
  },
];
h('span', { text: t(src.labelKey, src.label) });
```

### Orphan keys

`npm run i18n:audit -- --orphans` lists keys present in `en/` but referenced
nowhere — left behind by call sites that moved or died. They are harmless at
runtime but inflate all 12 locales and make "how translated are we?"
unanswerable, so the backlog (268 keys, ~2.6k entries across the locales) was
pruned to zero and the count is now **gated** alongside the hardcoded-copy
check.

When you delete or rename a call site, delete its key from all 12 locales in the
same commit. If a key genuinely must survive without a visible call site, add it
to the `orphans` map in `scripts/i18n-audit-allowlist.json` with a reason — same
burndown rules as `hardcoded`, including the stale-entry check.

The check is deliberately conservative: a key referenced by any dotted string
literal anywhere in `client/`, `shared/`, `server/`, `custom/` or `themes/`, or
matching a runtime-built family in `DYNAMIC_KEY_PATTERNS`, is never called an
orphan. So a hit is a real leftover — but if you add a `t()` family built from a
template literal, register it in `DYNAMIC_KEY_PATTERNS`
(`scripts/lib/i18n-keys.js`) or its keys will read as dead.

(`i18n-sync.js` copies English text into other locales, which makes them _look_
translated — prefer `i18n-fill.js --report`. `node scripts/i18n-sync.js
--dry-run` shows how much it would copy before you let it.)

## Dutch style

Dutch here borrows English freely; don't over-translate product vocabulary.

| Use                             | Not                     |
| ------------------------------- | ----------------------- |
| slide, slides                   | dia, dia's              |
| slide-type, slide-bibliotheek   | diatype, diabibliotheek |
| reactie (a comment)             | opmerking               |
| antwoord (a reply to a comment) | reactie                 |
| organization, lead, analytics   | werkruimte, …           |

Address the user informally (`je` / `jouw`, never `u`), use infinitives for
action labels (Opslaan, Annuleren, Verwijderen), and sentence case for
headings — Dutch does not capitalize every word.

## File Size

There is **no line limit on translation files**. The ~600-line rule of thumb
applies to hand-written files that carry logic — mostly JavaScript modules —
where length is a proxy for "too much going on to hold in your head". A locale
file is a flat, generated key/value map: it has no branching to follow, it is
never read top to bottom, and it grows by one line per key whether you like it
or not. Splitting it buys nothing and costs an entry in `I18N_COMPONENTS`
(`client/lib/ui-i18n.js`) plus one more HTTP fetch per page load.

The retired `i18n-validate` script used to fail the build over this and flagged
every locale on `slide-types.json`. It stopped checking line counts long before
B147 retired it altogether — every check it made is a test now.

## Supported Languages

Locales are **tiered**, and the tiers are the honest statement of what the app
promises about each. The canonical definition — the policy, the machine source
(`client/i18n/manifest.json`), and where each surface reads it — lives in
[`docs/reference/i18n-locale-tiers.md`](../reference/i18n-locale-tiers.md). In
short:

- **Tier 1 — `en`, `nl`:** complete and **gated**. Both define every key the
  code uses; `npm test` fails if one drifts (`tests/i18n-coverage.test.js` reads
  its required-locales list from the manifest's `tier` field).
- **Tier 2 — the other ten:** best effort. Partial, and they fall back to the
  English string in each `t()` call, so they degrade to English rather than
  breaking. Reported, never gated.

| Code | Language   | Tier | Status                                       |
| ---- | ---------- | ---- | -------------------------------------------- |
| en   | English    | 1    | Reference — complete, gated by tests         |
| nl   | Dutch      | 1    | Default UI locale — complete, gated by tests |
| de   | German     | 2    | Best effort — falls back to English          |
| fr   | French     | 2    | Best effort — falls back to English          |
| es   | Spanish    | 2    | Best effort — falls back to English          |
| it   | Italian    | 2    | Best effort — falls back to English          |
| pl   | Polish     | 2    | Best effort — falls back to English          |
| fi   | Finnish    | 2    | Best effort — falls back to English          |
| pt   | Portuguese | 2    | Best effort — falls back to English          |
| da   | Danish     | 2    | Best effort — falls back to English          |
| sv   | Swedish    | 2    | Best effort — falls back to English          |
| no   | Norwegian  | 2    | Best effort — falls back to English          |

The one way Tier-2's fallback breaks is a `t()` call written without its English
fallback (`t('some.key')` instead of `t('some.key', 'Some text')`) — then a
missing key renders the raw key string. An ESLint rule
(`no-restricted-syntax` on single-argument `t()`, scoped to `client/`) fails the
lint on that, so the fallback is never optional.

## RTL (Right-to-Left) Text Support

Slide content supports RTL languages (Arabic, Hebrew, Persian, Urdu) automatically. Users can type RTL text in any slide field and it will render correctly.

### How it works

All text elements in slide HTML use `dir="auto"`, which lets the browser detect text direction from the first strong directional character. This means:

- **Arabic/Hebrew text** → renders right-to-left
- **English/Dutch text** → renders left-to-right
- **Mixed content** → each element determines its own direction

No manual toggle is needed. Users just type in their preferred language.

### Technical implementation

1. **Slide type templates** (`shared/slide-types/types/*.js`): All text elements (`<h1>`, `<h2>`, `<p>`, `<div>` with text) include `dir="auto"`

2. **Markdown renderer** (`shared/markdown.js`): Generated elements (`<p>`, `<ul>`, `<ol>`, `<li>`, `<th>`, `<td>`) include `dir="auto"`. Code blocks keep `dir="ltr"` to preserve syntax direction.

3. **CSS** (`client/styles/slides/`): Uses `text-align: start` instead of `text-align: left` for direction-aware alignment

4. **HTML export** (`server/export/html.js`): Sets `dir` attribute on `<html>` element based on document language via `getDocDir()` from `server/utils/doc-lang.js`

### Supported RTL language codes

| Code | Language        |
| ---- | --------------- |
| ar   | Arabic          |
| he   | Hebrew          |
| fa   | Persian (Farsi) |
| ur   | Urdu            |

### Adding a new slide type

When creating a new slide type, ensure all user-facing text elements include `dir="auto"`:

```javascript
renderHtml: (content) => `
  <div class="slide slide-example">
    <h2 class="heading" dir="auto">${esc(content?.title)}</h2>
    <p class="body" dir="auto">${esc(content?.body)}</p>
  </div>
`;
```
